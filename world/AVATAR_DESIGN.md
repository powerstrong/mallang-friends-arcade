# 광장 아바타 꾸미기 시스템 — 설계서 (v2, 확정)

> 상태: **확정** — claude 초안(v0) + codex 설계안(R0) 병합, codex 생산 관점 검토(R1 "조건부 Go") 반영, codex 최종 confirm(R2 **"Go"**, 2026-08-17). §15 협의 로그 참조.
> 대상: 텐텐오락실 광장(world/)에 사람 아바타 + 꾸미기 도입.
> 사용자 맥락: 아빠 + 두 딸이 노는 가족 게임. 꾸미기를 좋아하는 아이들이 주 사용자.

## 0. 한 문장 정의

이 시스템은 **수집 경제가 아니라 "디지털 인형놀이"** 다 — 아이들은 언제든 자유롭게 조합하고, 가족이 가끔 새 옷을 선물한다. 노가다·가챠·경쟁 요소는 설계에서 배제한다.

## 1. 원칙

1. **움직임 품질 최우선**: 앞/옆/뒤 3방향 걷기가 어떤 착장에서도 어긋나지 않는다. 정합이 불안한 화려함보다 정합이 보장되는 단순함.
2. **노가다 금지**: 옷 획득을 반복 플레이·승리와 연결하지 않는다(자매 경쟁 유발 방지). 대부분 무료 + 아빠 선물.
3. **기존 구조 재사용**: 3×3 시트, 클라 전용 부스 패턴(LAB_BOOTH), D1, imagegen 파이프라인.
4. **기존 게임 무파괴**: 미니게임 캐릭터 선택은 그대로 작동해야 한다.
5. **정합의 원천은 등록(registration) 규칙**: "레퍼런스를 참고해 다시 그리기"가 아니라 **정본 바디 시트를 편집 대상으로 고정**하고, 머리·얼굴·발 기준점을 픽셀 단위로 지키는 생산 규율이 이 시스템의 성패를 가른다(§12).

## 2. 역할 분리 — 광장 아바타 vs 말랑 친구

| 구분 | 내용 |
|---|---|
| **광장 아바타** | 로비를 걸어 다니는 사람 캐릭터(꾸미기 대상). 광장 전용 |
| **말랑 친구** | 미니게임에 데려가는 기존 동물 5종(라떼·토끼·햄스터·고양이·병아리) |

- 화면 설명: "광장에서는 내가 만든 캐릭터로 놀아요. 게임에서는 선택한 말랑 친구와 함께해요."
- 데이터: 광장 착장(`outfit`)과 `gameBuddyId`를 분리 저장. 기존 `gameIds` 매핑은 말랑 친구의 것을 사용 — **게임 코드는 변경 없음**.
- **A단계 실측으로 축소(2026-08-17)**: 어떤 게임 클라도 발사 URL 의 `characterId` 를 읽지 않는다(점프·계단=자체 선택 화면, 쓱쓱=서버 배정). 따라서 **말랑 친구 사전 선택 UI 는 두지 않는다** — 게임 캐릭터는 각 게임이 스스로 결정. `gameBuddyId` 는 프로토콜/서버 기본값(무효·부재 → 랜덤 동물)으로만 유지해, 미래에 URL 캐릭터를 읽는 게임이 생기면 그때 UI 를 복귀한다.
- 동물을 광장 캐릭터로 쓰는 기존 방식도 유지(동물 선택 시 꾸미기만 비활성). 스프라이트 로딩 실패·구버전 데이터의 폴백도 말랑 친구 표시.
- 미니게임의 사람 아바타 지원 통합은 먼 미래 과제로만 남긴다.

## 3. 사람 아바타 — 단일 ID + 남녀 프리셋, 유니섹스 공용 바디

- **내부 ID는 `human` 하나.** 남자아이/여자아이는 캐릭터 종이 아니라 **초기 프리셋**(기본 헤어+기본 코디 번들)이다. 피커에는 남/녀 2카드를 보여주되, 선택 결과는 `characterId:'human'` + 프리셋 outfit으로 저장된다. (codex R1: 이후 자유 코디와 데이터 의미가 깔끔)
- **프리셋 이름(2026-08-17 확정, 1회 개명)**: 여자아이 = **젤리**(말랑말랑), 남자아이 = **쿠키** — 간식 듀오, 말랑프렌즈 음식 명명(라떼·모찌·푸딩·민트·피치) 계승. (솜이는 사용자 반려.) 카드에는 이름 + "여자아이/남자아이 · 꾸미기" 안내 줄. 이름의 단일 진실은 `shared/wardrobe_catalog.js` presets(label·sub·emoji).
- **바디 템플릿 1종** — 같은 키·관절·발 기준점·충돌 크기. 에셋은 물리적으로 남녀 호환(같은 바디에 맞음).
- ~~성별은 프리셋일 뿐 의상을 제한하지 않는다~~ → **개정(2026-08-17, 사용자 확정)**: 옷은 성별 태그로 노출을 구분한다 — `fit: girl|boy|all`. 치마·원피스류는 girl, 남아 전용 라인 별도 생산, 기본류(티셔츠·청바지 등)는 all. 필터는 UI 레벨(프리셋 기준), sanitize 는 비노출 원칙만 강제(관대). 상세 = AVATAR_NEXT_STEPS.md P0-2.
- **첫 접속 흐름(확정)**: 저장된 아바타가 없으면(완전 첫 접속) 피커에서 남/녀 프리셋을 **반드시 직접 고른다**(무선택 기본값 없음). 프리셋(성별)은 **이후 언제든 변경 가능** — 피커 재진입 또는 꾸미기 패널의 프리셋 스위치(해당 프리셋의 기본 헤어+기본 코디 재적용).
- **마네킹 비노출 원칙(확정)**: 민머리+속옷의 정본 바디는 **생산 내부 전용**이다. 사용자에게 보이는 아바타는 어떤 경우에도 기본 헤어+기본 코디 이상을 갖춘다 — outfit 데이터가 없거나 무효하면 프리셋 기본값을 강제 적용하고, 레이어 로딩 실패 시에도 마네킹 단독 노출 대신 완성된 기본 착장(또는 말랑 친구 폴백)을 보여준다.
- 피부톤·얼굴 variant: v1 제외(베이크 방식의 구조적 제약). 귀여운 고정 얼굴 1종. v2에서 레이어 분리 검증 후 도입.

## 4. 슬롯 구조

**v2: 6슬롯** (2026-08-17 상·하의 분리 조기 도입 — 사용자 지시. 착용-차분 추출로 정합 실측 통과)

| 슬롯 | 내용 | 에셋 형태 |
|---|---|---|
| **한벌옷(outfit)** | 원피스·세트옷 통짜 | 전신 시트(바디 포함, §5) |
| **상의(top)** | 티셔츠 등 | 투명 레이어(정본 바디의 흰 탱크톱을 **완전히 덮는** 실루엣만) |
| **하의(bottom)** | 바지·치마 | 투명 레이어(회색 반바지를 **완전히 덮는** 실루엣만) |
| **헤어** | 스타일 + 색(팔레트 ID) | 투명 레이어 — 내부적으로 **back/front 2파트**(§5) |
| **모자·머리핀** | 머리 상단 부착물 | 투명 레이어 |
| **얼굴 소품** | 안경 등 | 투명 레이어 |

- **착장 규칙: 한벌옷 XOR (상의 AND 하의)** — 어느 쪽도 완전하지 않으면 프리셋 기본 한벌옷 강제(sanitize, §3 비노출 원칙의 연장). 분리옷 렌더는 **정본 바디를 바닥 레이어(피부 역할)** 로 깔고 하의→상의 순서로 얹는다 — 정본 바디 "단독" 렌더는 여전히 금지.
- 모자+안경 동시 착용 가능(중첩 조합 재미). 헤어·모자 충돌은 카탈로그 호환 규칙으로 관리(예: 대형 모자는 묶음머리와만).
- v3+ 확장 경로: 등 소품(백팩), 손 소품, 신발 분리, 피부/얼굴 variant. **레이어 정합이 검증된 뒤에만** 연다.

## 5. 렌더링 — 레이어 합성 (베이크 + 머리 레이어)

**핵심: 착장이 바뀔 때 한 번만 합성하고, 프레임마다는 지금처럼 시트 1장을 그린다.**

1. 그리드는 기존과 동일한 **3×3** (row0=정면, row1=측면 우향, row2=뒷면 / col0=정지, col1·2=걷기 A/B). 좌측은 미러.
2. **코디 시트 = "민머리 정본 바디가 그 옷을 입은 전신 시트"**. 한 이미지 안에서 생성되므로 몸-옷 정합이 구조적으로 보장된다. 단, 이 보장은 몸↔옷 사이에만 성립하고 **코디 시트끼리의 두상·얼굴 정합은 생산 규율(§12)로 강제**해야 한다(codex R1).
3. 합성 z-order: **`hair_back → 코디(바디 포함) → hair_front → 얼굴 소품 → 모자`**. 긴 머리를 단일 전면 레이어로 두면 앞·옆 모습에서 어깨 뒤로 가야 할 머리가 몸을 덮으므로, 헤어 1아이템 = back/front 2파트로 분리한다(슬롯 수는 그대로 1개).
4. 합성 결과를 그 플레이어의 `sprite.img`로 사용 — `drawAvatar()`는 사실상 무변경, **프레임당 비용 증가 없음**. 코디별 헤어 오프셋 런타임 보정은 **금지**(조합 수만큼 예외가 늘어난다) — 오프셋이 필요한 시트는 불합격 처리한다.
5. 치마·긴 머리의 흔들림은 **프레임에 미리 그려 넣는다**(런타임 물리 없음).
6. **걷기 재생 개선(무비용)**: 현재 A↔B 2박자 대신 기존 정지 프레임을 통과 자세로 재사용한 **`A → idle → B → idle` 4박자**를 0단계에서 시험한다(재생 간격 110~150ms 비교). 그래도 뻣뻣하면 그때만 **4열×3행**(걷기 A/passing/B, 재생 A→passing→B→passing)으로 증설 — 셀 33% 증가로 imagegen 일관성 위험이 커지므로 최후 수단. 명칭은 cols×rows 순서로 `_4x3`.
7. **배포 전 오프라인 정규화**: 원본 1024~1254² 시트를 그대로 싣지 않는다(디코드 약 6MB/장 — 모바일 메모리 압박). 배포용 아틀라스는 **384×384(셀 128px)로 사전 정규화**해 모든 레이어가 동일 규격을 공유하게 한다. 실제 렌더는 100×100이므로 충분.
8. **합성 캐시**: 키 = 슬롯 고정 순서 + 팔레트 ID + `catalogVersion`. **LRU 16~32개 제한**. 광장 인원 대비 충분하고 메모리 폭주를 막는다.
9. **지연 로딩 + 원자 교체**: 필요한 착장 조합의 레이어만 로드하고, 합성 완료 전까지는 기존(또는 기본) 아바타를 유지하다가 완료 시 한 번에 교체 — 깜빡임 방지.

## 6. 꾸미기 진입 — 옷방(별도 맵) 없음

**별도 옷방 맵은 만들지 않는다.** 이동 강제·로비 분리·모바일 로딩 증가 대비 이득이 없다. 대신 같은 꾸미기 패널을 여는 진입점 2개:

1. **헤더 `👕 꾸미기` 버튼** — 어디서든 즉시(편의).
2. **광장의 옷장·전신거울 오브젝트** — 걸어가서 열기(LAB_BOOTH와 같은 클라 전용 오브젝트, 서버 zone 아님). "여기서 갈아입는다"는 놀이 감각.

꾸미기를 여는 동안 광장 접속은 유지된다(모달 패널, WS 끊김 없음).

향후 딸들이 꾸미기를 특히 좋아하면 "패션 스튜디오"(코디 비교·사진·패션쇼)라는 **놀이 공간**으로 확장 — 필수 기능과 놀이 공간을 분리한다.

## 7. 꾸미기 패널 UX

모바일 전체화면에 가까운 슬라이드업 패널(세로 우선).

- **중앙: 큰 전신 미리보기** — 현재 착장으로 걷기 애니메이션 재생, 탭하면 앞→옆→뒤 회전.
- **하단: 큰 아이콘 탭** — 코디 / 헤어 / 모자·핀 / 얼굴 소품 (+ 쿠폰·선물함 탭).
- **입어보기 자유**: 잠긴 옷도 미리보기에서 자유롭게 착용 가능. 쿠폰은 "이 옷 받기" 확정 시에만 소모.
- **잠긴 아이템과 저장**: 잠긴 아이템은 **개별 "받기" 완료 후에만 저장 가능**. 저장 버튼이 여러 쿠폰을 한꺼번에 소모시키는 일은 없다(아이에게 예상 밖 지출 방지). 잠긴 상태로 저장 시도 → 해당 아이템만 하이라이트하고 안내.
- 되돌리기(편집 전 상태로), **오늘의 랜덤 코디** 버튼(보유템 랜덤 조합), 좋아하는 코디 저장 3칸(B단계).
- **저장 시 일괄 반영**: 편집 중에는 다른 플레이어에게 기존 코디가 보이고, 저장 시 한 번에 바뀌며 작은 반짝임 이펙트. 편집 중간 상태를 서버로 보내지 않는다.
- **초안 처리**: 닫기·뒤로가기·연결 오류 시 기존 착장 유지. 저장 실패 시 패널과 편집 초안을 그대로 보존.
- 접속 전 캐릭터 피커는 아바타 종류 선택만(동물 5 + 남/녀 프리셋). 마지막 저장 착장 자동 적용 — 입장 전 단계를 무겁게 만들지 않는다.

## 8. 옷과 재화 — "옷 쿠폰" 단일

재화는 **옷 쿠폰 🎟️ 하나만.** 동전·보석·경험치·조각 등 다중 재화 없음. 티켓·일일획득 같은 플레이 연동 재화도 **도입하지 않는다**(반복 유도·자매 경쟁 방지).

| 원칙 | 내용 |
|---|---|
| 무료가 기본 | 기본 외형·기본 옷 전부 무료. **아이템 수 기준 무료율 70% 이상 상시 유지** — 잠금 아이템 1개를 추가할 때마다 무료 아이템도 3~4개 누적한다(수치 충돌 방지 규칙, codex R1) |
| 가격 단일화 | 잠긴 옷은 **전부 쿠폰 1장**. 아이가 가격을 계산하거나 참게 만들지 않는다 |
| 색상 포함 | 한 스타일 해금 = 모든 색상 사용 가능 |
| 없음 | 뽑기, 중복, 쿠폰 유효기간, 기간 한정 판매, 출석 연속 보상, 거래·양도, 현금 결제 |

무료 지급(가벼운 서프라이즈, 조건 없음):
- 새 프로필 생성 시 쿠폰 2장
- **주간 무료 옷 = 그 주부터 영구 무료 카탈로그에 추가**되는 방식(그 주에만 수령 가능한 한정이 아님 — FOMO 금지 원칙과 정합)
- 생일·명절·여름·크리스마스 무료 세트

**A단계는 쿠폰 시스템 없이 전부 무료로 출시**한다. 딸들이 실제로 어떤 옷을 즐겨 입는지 본 뒤, 특별한 새 옷이 생겼을 때 쿠폰을 도입한다(B단계).

## 9. 아빠(부모) 선물 흐름

부모 메뉴(PIN)에 딱 4기능:

1. 아이 프로필 선택
2. 쿠폰 1장 또는 3장 선물
3. 특정 옷 한 벌 바로 선물
4. 선택적 짧은 메시지 첨부 — "오늘 정리를 도와줘서 고마워!" / "약속을 잘 지켜서 주는 선물이야."

- 전달: 아이의 **선물함**에 도착 → 선물상자 개봉 연출과 메시지 표시.
- 보조: **종이 쿠폰용 코드 발행** — 코드를 종이에 적어 현실에서 건네고, 아이가 쿠폰 탭에 입력해 받는 의식(ritual)도 지원. 내부적으로 선물함과 같은 지급 로직.
- **게임이 아이의 행동을 감시·판정하지 않는다.** 아빠가 현실에서 판단하고 수동으로 선물한다. 쿠폰은 노동의 대가가 아니라 "고마움을 표현하고 아이가 원하는 선물을 직접 고르게 하는 수단."

## 10. 프로필과 저장 — 가족 프로필 (D1)

옷장 소유를 저장할 신원이 필요하다. **경량 가족 프로필** 도입(넷플릭스 스타일 카드 선택).

- **신원은 불변 `profile_id`** — 이름은 변경 가능한 표시값일 뿐, 신원으로 쓰지 않는다(codex R1). 리더보드 `player_name` 연결은 장기적으로 선택적 `profile_id` 컬럼 추가로 해결(당장은 미연결).
- 접속 화면: 프로필 카드 선택 → `world_name` 자동 입력. 프로필 생성·관리는 부모 메뉴에서(가족 규모 N≤10).
- **게스트 모드 유지**: 이름만 치고 입장(현행 동일) = 무료템만, 저장 없음. 친구 방문용.
- A단계(프로필 이전)에는 착장을 localStorage에 저장 — 기기별 유지, 서버 저장은 B단계부터.
- **부모 PIN 보안(B단계)**: PIN 해시만으로는 온라인 무차별 대입을 못 막는다 — 서버 측 시도 제한·지연·일시 잠금 + 세션 토큰. **`ADMIN_KEY`류 시크릿을 브라우저 코드에 넣지 않는다.**
- **원자성·멱등성**: 쿠폰 차감+옷장 삽입, 선물 코드 선점은 단일 트랜잭션/조건부 UPDATE로 처리 — 이중 탭·두 기기 동시 요청에도 중복 차감/중복 수령 없음.

```sql
-- 0005_create_profiles.sql (안)
CREATE TABLE profiles (
  id INTEGER PRIMARY KEY AUTOINCREMENT, -- 신원(불변)
  name TEXT NOT NULL UNIQUE,            -- 표시 이름(변경 가능, 가족 규모라 UNIQUE 유지)
  lobby_avatar TEXT,                    -- 'human' | 동물 worldId
  game_buddy TEXT,                      -- 말랑 친구 worldId
  outfit_json TEXT,                     -- {outfit, hair, hairColor(팔레트ID), hat, faceAcc} + 저장 코디 3칸
  coupons INTEGER NOT NULL DEFAULT 0,
  pin_hash TEXT,                        -- 부모 프로필만 사용(B단계, 서버 측 잠금과 병행)
  created_at INTEGER NOT NULL
);
CREATE TABLE closet (
  profile_id INTEGER NOT NULL,
  item_id TEXT NOT NULL,
  source TEXT NOT NULL,                 -- 'free' | 'coupon' | 'gift' | 'code'
  acquired_at INTEGER NOT NULL,
  PRIMARY KEY (profile_id, item_id)
);
CREATE TABLE gifts (                    -- 선물함 + 종이 쿠폰 코드 겸용
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  code TEXT UNIQUE,                     -- NULL=선물함 직행, 값 있으면 코드 입력형 (예: MZ7-K2P)
  target_profile INTEGER,               -- NULL=코드 입력자 아무나 1회
  payload_json TEXT NOT NULL,           -- {coupons:3} | {itemId:'outfit_sailor'}
  message TEXT,
  issued_at INTEGER NOT NULL,
  claimed_by INTEGER, claimed_at INTEGER -- 수령은 조건부 UPDATE로 선점(중복 수령 방지)
);
```

## 11. 서버/프로토콜 변경

- **카탈로그 단일 진실**: 이상적으로는 클라/서버가 **하나의 카탈로그 모듈(ESM)** 을 공유. 번들 제약으로 미러가 불가피하면 characters.js 패턴을 따르되 **CI에서 양쪽 내용 해시 비교**를 강제(assert 함수 + 테스트). 아이템 id·슬롯·무료 여부·호환 규칙·`assetVersion` 포함.
- world WS join payload(안):
  ```js
  { characterId: 'human',            // 또는 동물 worldId (하위 호환)
    gameBuddyId: 'mint_kitten',      // 말랑 친구 — 게임 입장 변환에만 사용
    outfit: { outfit:'sailor', hair:'twin_long', hairColor:'rose', hat:null, faceAcc:null },
    catalogVersion: 1 }
  ```
- 서버 attachment에는 둘 다 저장하되, **광장 브로드캐스트에는 `characterId`/`outfit`만**, **게임 입장 변환에는 검증된 `gameBuddyId`만** 사용한다. `characterId`가 사람인데 `gameBuddyId`가 없거나 무효면 서버가 랜덤 동물로 폴백(현행 `isValidCharacterId` 폴백 관례).
- `outfit_change` 메시지: 저장 시에만 발신. **단조 증가 `revision`** 포함 — 역순 도착 방지. 서버는 아이템 id·슬롯·팔레트 ID·호환 규칙·payload 크기를 전부 검증 후 브로드캐스트. 수신 피어는 재합성.
- 재접속용 `joinParams`도 저장 직후 새 outfit으로 갱신(구버전 착장으로 재입장하는 버그 방지).
- wire 플레이어 상태: `{id, name, characterId, outfit?, x, y, dir, moving}` — 동물이면 `outfit` 없음(하위 호환).
- REST(`/api/*`, game-lobby 워커): `GET/POST /api/profile`, `GET /api/closet`, `POST /api/closet/claim`(쿠폰 소모), `POST /api/gift/claim`(선물함/코드), `/api/admin/*`(부모 메뉴 — B단계, §10 보안 규칙 적용).
- 게임 쪽 변경: **없음**(말랑 친구 매핑 그대로).

## 12. 에셋 생산 파이프라인 (codex imagegen) — 등록 규율

기존 워크플로(imagegen → `chroma_remove.py` → `world/assets/`)를 다음 규율로 확장한다. **핵심: 레퍼런스 참고 생성이 아니라 "정본 편집(edit target)" 접근.**

### 12.1 정본 바디
1. **바디 정본 시트 1장**: 민머리+고정 얼굴+중성 속옷(민소매 상의+반바지 수준)의 사람 아이 치비 3×3. 기존 동물과 같은 스타일(큰 머리, 셀 높이 75~80%, 발 하단 정렬). 승인까지 3~6회 생성 각오(가장 중요한 1장). **사용자 비노출** — §3 마네킹 비노출 원칙.
2. 프롬프트에서 이 캐릭터를 "남자아이/여자아이"가 아니라 **"정본 아바타" / "고정 마네킹 바디"** 로 부른다 — 모델이 헤어를 자동 보충하는 경향을 줄인다.

### 12.2 코디 시트 — 편집 대상 방식
3. 코디 생성은 "이 캐릭터를 참고해 그려라"가 아니라: **"Image 1(정본 바디 시트)을 편집하되 의복만 변경하라. 9셀의 캔버스·셀 순서·포즈·머리 중심·두상 윤곽·얼굴·피부·손·발 기준점은 변경하지 않는다. 완전히 매끈한 민머리를 유지하고 머리카락·앞머리·잔머리·머리 장식을 어느 셀에도 추가하지 않는다. 같은 아이를 재해석하거나 다시 디자인하지 않는다."** 매 호출마다 불변 조건을 반복한다.
4. 스타일 레퍼런스를 함께 쓸 때는 역할 명시: Image 1=기하·얼굴 정본(최우선), Image 2=채색·외곽선 스타일만 참고.
5. 알려진 실패 모드(검수 시 중점 확인): 두상 폭/높이 변동, 머리 중심 이동, 목·어깨 높이 변동, 얼굴 재그리기, 일부 셀에만 머리카락 생성, 프레임 간 치마 길이/무늬/단추 수 변동, 측면 방향 반전(라떼 강아지 전례), 그림자/바닥면 생성.

### 12.3 헤어·모자·안경 레이어 — 착용 편집 + 차분 추출 (0단계 실측으로 확정)
6. ~~아이템만 떠 있는 레이어를 직접 생성~~ → **폐기.** 0단계 실측에서 위치·크기 앵커 실패(긴머리 분량 폭주, 숏컷이 얼굴을 덮음, 베레모 거대화)가 재현됐다. **확정 흐름: 정본 마네킹이 "착용한" 모습을 편집 생성(§12.2와 동일 방식, 실측 정합 0.5~1.5px) → 정본과의 픽셀 차분으로 아이템만 추출**(`process.py --extract-worn`).
   - 차분 추출은 이력(hysteresis)+형태 필터: 신규 실루엣·강한 차이를 시드로, **2회 침식을 견디는 두꺼운 약영역만 인정** — 모델이 전신 음영을 미세 재작화해 생기는 얇은 고스트 윤곽선을 걸러낸다(실측 실패 모드).
   - 착용 시트가 9셀 전부 정합을 유지하므로(걷기 셀 머리중심 Δ0~1px 실측) 3뷰 복제가 불필요하다 — 걷기 셀의 미세 찰랑임도 살아남는다.
7. 헤어는 추출 후 **턱선(정본 콘텐츠 top+50%) 기준 front/back 자동 분리**(`--split-hair`, §5 z-order). 뒷모습 행은 전부 front. 안경·모자는 단일 레이어.

### 12.4 헤어 색 — 팔레트 매핑 (AI 재생성 금지)
8. 색상별 AI 재생성은 하지 않는다(색만 바뀌어야 하는데 형태·앵커까지 변해 QA가 색상 수만큼 늘어난다). **중성 마스터 1장 → 명도 3단계 분류(highlight/base/shadow) + 외곽선 보존 → 팔레트 치환 PNG를 빌드 시 결정적으로 사전 생성.** 단순 multiply는 금발·옅은 파스텔이 탁해지므로 쓰지 않는다.
9. 색은 자유 문자열이 아니라 **팔레트 ID**(`rose|mint|choco|...`)로 제한. 무지개·옴브레 같은 공간 패턴 헤어만 별도 생성 예외.

### 12.5 후처리·QA 게이트
10. **크로마키 개선**: 현재 `chroma_remove.py`는 전역 녹색 우세 픽셀을 제거해 **민트색 옷·녹색 소품이 손상될 수 있다**. 아이템 팔레트에 따라 녹색/마젠타 키를 선택하고, 전역 색 판정 대신 **테두리에서 연결된 배경만 제거**하는 방식으로 보강한다.
11. **정규화**: 승인된 시트는 배포 규격 384×384로 오프라인 정규화(§5-7). 셀별 위치·크기 보정도 이 단계에서.
12. **QA 게이트** — `world/wardrobe-preview.html`(로컬 전용)에서 조합 오버레이 + 걷기 재생 육안 검수 + 수치 기준:
    - 정규화 후 머리 중심 오차 ≤1px, 두상 바운딩박스 폭·높이 오차 ≤1px
    - 발 기준선 오차 0px
    - 반투명 오버레이에서 얼굴 이중상 없음
    - 셀 경계 알파 침범 없음, 측면 방향·셀 순서 고정
    - **통과 못 하면 재생성** — 런타임 오프셋 보정으로 구제하지 않는다. "단독으로 예쁜 이미지"와 "조합 가능한 게임 에셋"은 합격 기준이 다르다.

### 12.6 물량 현실치 (codex R1 추정)
- 0단계: 생성 8~15회, 4~8시간 — 하루짜리 검증.
- A단계 전체(마스터 15~17장): 생성 25~45회, 14~24시간 — 집중 2~4일. 승인 시트당 1.5~3회 생성으로 계획.
- 팔레트 매핑 채택으로 색상별 헤어 재생성(+1~2일)을 회피한 것이 규모 통제의 핵심.
