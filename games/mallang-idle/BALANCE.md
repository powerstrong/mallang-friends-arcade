# 말랑프렌즈 키우기 — 밸런스

`mallang-idle` · 공식 · 상수 · 시뮬레이터 지표

> 이 프로젝트가 실패한다면 구현 난이도가 아니라 **성장 곡선이 재미없어서**다.
> 밸런스는 코드 작업이 아니라 **측정 작업**이다.

---

## 1. 절대 규칙

1. **모든 계수는 `BALANCE` 한 곳에.** 게임 코드에 `* 1.17`, `* 6`, `* 0.25` 같은 매직 넘버가
   흩어지는 순간 밸런싱이 지옥이 된다.
2. **엔진은 순수 결정론.** `Math.random()` 금지, seeded RNG만 사용. DOM·타이머·`Date.now()`를
   엔진이 직접 읽지 않는다(시간은 인자로 주입).
3. **시뮬레이터와 게임은 같은 엔진을 쓴다.** 전투 로직이 두 벌 존재하면 지표가 거짓말을 한다.
4. **밸런스를 바꾸면 시뮬을 다시 돌리고 지표 변화를 커밋 메시지에 적는다.**

## 2. 상수

실제 값은 항상 [engine/balance.js](engine/balance.js)가 원본이다. 아래는 2026-08-15
그리드 서치로 채택한 값이다(무빌드 저장소라 ES module 이 아니라 UMD 패턴을 쓴다).

```js
// engine/balance.js — 발췌
var BALANCE = {
  // ── 플레이어 ──────────────────────────────
  baseAtk: 10,
  atkGrowth: 1.12,          // 지수 (레벨당)

  baseAspd: 1.0,            // 공격/초
  aspdPerLv: 0.04,          // 선형 증가분
  aspdCap: 5.0,             // 상한 — DPS 이중 지수 폭주 방지

  goldMulPerLv: 0.08,       // 선형: goldMul = 1 + 0.08*(lv-1)

  // ── 적 ────────────────────────────────────
  mobBaseHp: 30,
  mobHpGrowth: 1.18,        // 스테이지당 지수
  bossHpMultiplier: 12,
  bossTimeLimit: 25,        // 초
  mobsPerStage: 10,
  advanceSeconds: 0.6,      // 몹 간 전진 시간 — 진행의 리듬

  // ── 보상 ──────────────────────────────────
  goldBase: 6,
  goldGrowth: 1.158,        // 스테이지당 지수 (적 HP 성장보다 낮게)

  // ── 강화 비용 ─────────────────────────────
  costBase:   { atk: 20,    aspd: 60,   gold: 45 },
  costGrowth: { atk: 1.15,  aspd: 1.22, gold: 1.18 },

  // ── 오프라인 ──────────────────────────────
  offlineEfficiency: 0.25,
  offlineMaxHours: 8,
};
```

**유물 (P3):** 별조각(보스 드랍, 실패에도 지급) + 유물 3종. 배수는 레벨당 곱연산
(`pow(1+perLv, lv)`) — 선형이면 상대 이득이 줄어 지수 벽을 못 따라간다. 상수는
`BALANCE.relics` / `shardClearDiv` / `shardFailDiv`. P2 편성 + P3 유물 도입 후
`tune.js` 재서치로 mobHpGrowth 1.18 · goldGrowth 1.158 채택(2026-08-15).

**채택 근거**: `tools/tune.js` 로 120개 조합을 평가한 1위 조합.
초기값(`1.18 / 1.16 / 7 / 1.15`)은 5분 구간에 벽이 아예 없고(보스 실패 0회)
24시간 지점에서 갑자기 74분 벽이 생기는 곡선이었다 — "벽이 없다가 갑자기 영원히 막히는"
전형적 실패 모드. 채택값은 5분~2시간 구간에서 최장 벽 50초대를 안정적으로 유지한다.

### 공식

```
atk(lv)      = baseAtk * atkGrowth^(lv-1)
aspd(lv)     = min(aspdCap, baseAspd * (1 + aspdPerLv*(lv-1)))
goldMul(lv)  = 1 + goldMulPerLv*(lv-1)
dps          = atk(atkLv) * aspd(aspdLv)

mobHp(s)     = mobBaseHp * mobHpGrowth^(s-1)
bossHp(s)    = mobHp(s) * bossHpMultiplier
mobGold(s)   = goldBase * goldGrowth^(s-1) * goldMul(goldLv)

cost(axis,lv)= costBase[axis] * costGrowth[axis]^(lv-1)
```

### 곡선 간 관계 — 여기가 재미의 전부

| 관계 | 의도 |
|---|---|
| `mobHpGrowth(1.18)` **>** `goldGrowth(1.16)` | 스테이지가 오를수록 서서히 벽이 생긴다. 방치형의 기본 텐션 |
| `costGrowth.atk(1.15)` **>** `atkGrowth(1.12)` | 한 레벨의 실질 이득이 체감한다 → 다른 축을 볼 이유가 생긴다 |
| `bossHpMultiplier(12)` | 일반몹 12마리분. 파밍 구간과 관문의 대비를 만든다 |
| `aspdCap` | ASPD가 무한 성장하면 ATK 축이 무의미해진다 |

**이 숫자들은 정답이 아니라 출발점이다.** 판정은 아래 지표가 한다.

## 3. 시뮬레이터

```bash
node games/mallang-idle/tools/sim.js --minutes=30
node games/mallang-idle/tools/sim.js --hours=24 --json
node games/mallang-idle/tools/tune.js --top=5     # 파라미터 그리드 서치
```

24시간 시뮬이 0.2초에 돌기 때문에 손으로 상수를 바꿔가며 감으로 맞추지 않아도 된다.
`tools/tune.js` 가 조합을 수백 개 돌려 목표 지표 이탈도를 점수화한다(120조합 11.6초).

UI를 3시간 플레이하며 곡선을 보는 것은 자동 개발에서 **불가능하다.**
시뮬레이터가 에이전트의 유일한 피드백 채널이다.

### 시뮬레이터 AI 정책 (플레이어 대역)

시뮬레이터는 "합리적인 플레이어"를 대역한다. 정책 자체도 상수로 노출한다.

- 기본 정책: **가성비 최대 축에 투자** (비용 대비 DPS 증가량, GOLD는 회수기간으로 환산)
- 보스 실패 시: 예상 돌파 DPS에 도달할 때까지 파밍 후 재도전
- 정책을 바꾸면 지표가 바뀐다 → 정책 변경도 커밋에 기록한다

### 출력 예시

```
=== simulate 30m (seed=7) ===
Stage        1 → 76
ATK Lv.35  ASPD Lv.9  GOLD Lv.17
강화 횟수    61        보스 시도 12 (성공 9 / 실패 3)
최장 벽      2m 14s  @ Stage 61
분당 골드    1.4K → 88K
유휴 시간    11%
```

## 4. 지표와 허용 범위 (회귀 테스트)

`tests/balance.test.js`가 아래를 검사한다. **벗어나면 실패로 떨어뜨린다.**
자동 에이전트가 밸런스를 조용히 망가뜨리는 것을 막을 유일한 방법이다.

| 지표 | 허용 범위 | 벗어나면 |
|---|---|---|
| 첫 강화까지 | `< 15초` | 도입이 지루함 |
| 첫 보스 도달 | `30~90초` | 목표 제시가 늦음 |
| 첫 보스 돌파 | `< 3분` | 초반 벽이 너무 높음 |
| 스테이지당 평균 체류 (5분/30분) | `20~75초` / `20~90초` | 진행감 상실 |
| 최장 벽 (30분 / 2시간) | `< 5분` / `< 10분` | 이탈 지점 |
| 최장 벽 (24시간) | `< 75분` (4,500초) | 아래 주석 참고 |
| 유휴 시간 비율 | `< 30%` | 할 게 없어 끄는 구간 |
| 돌파 여유비 | `1.0~1.7` | 보스가 체크로 기능하지 않음 |
| 24h 시뮬 완주 | 예외 없이 종료 | 오버플로 · 무한루프 |

**지표 정의 두 가지가 처음 생각과 달랐다.**

- **유휴 비율** — "지금 살 수 있는 강화가 없는 시간"으로 재면 항상 100%가 나온다.
  구매 직후는 언제나 골드가 부족하기 때문이다. 방치형에서 골드가 모이는 짧은 대기는
  정상이므로, **다음 강화까지 예상 대기가 `SIM_POLICY.idleThresholdSec`(30초)를
  넘는 시간**만 유휴로 집계한다.
- **돌파 여유비** — `(DPS × bossTimeLimit) / bossHp`. 돌파하는 순간은 정의상 성공한
  순간이라 이 값은 항상 1 이상이다. 원래 적었던 `0.8~1.2`는 달성 자체가 불가능한
  범위였다. 1.0 에 가까울수록 아슬아슬하게 잡았다는 뜻이고, 너무 크면 보스가
  관문 구실을 못 한다.

**24시간 벽을 75분으로 둔 근거 (P3 이후 재확정, 2026-08-16)** — P1 시점의 목표는
60분이었고 "P3 가 벽을 무너뜨리면 20분으로 되돌린다"고 적었다. P3(유물) 실측 결과는
반대였다: 나침반 비용은 지수, 조각 수입은 선형이라 **연속 플레이 기준 하루 벽 ~50분은
구조적 하한**이다(유물 포함 120조합 재서치로 확인). 현재 실측 최장 벽은 67분이고,
테스트 방어선은 4,500초(75분) — "유물 경제가 고장나면 즉시 잡는" 기준이다.
이 구간은 오프라인 보상으로 넘기는 것이 장르의 의도이며, 시뮬은 오프라인을 모델링하지
않아 비관적이다. 60분 목표를 다시 논하려면 **시뮬에 오프라인 세션 모델을 먼저 넣고**
"활동 시간 기준 벽"으로 재야 한다(NEXT_STEPS 밸런스 후속 항목).

**벽 체류(wallRatio)** — 유휴 비율은 "살 것이 없는 시간"만 재므로 67분짜리 벽에서도
0%가 나온다(골드는 계속 흐르니까). 장기 정체감은 `벽 체류 = 보스 첫 실패 → 돌파까지의
누적 시간`으로 따로 관찰한다(24h 실측 ~83%). 아직 게이트는 아니고 관찰 지표다 —
오프라인 모델 없이 상한을 정하면 연속 플레이 가정의 왜곡이 그대로 기준이 된다.

### 허용 범위를 고칠 때

지표가 실패하면 **먼저 상수를 고친다.** 허용 범위를 넓히는 것은
"이 범위 자체가 틀렸다"는 근거가 있을 때만이고, 그때는 근거를 커밋 메시지에 남긴다.
범위를 조용히 넓혀 테스트를 통과시키는 것은 이 프로젝트에서 가장 해로운 행동이다.

## 5. 숫자 표기

```
1 → 999 → 1.00K → 1.00M → 1.00B → 1.00T → 1.00aa → 1.00ab → ...
```

- 표기 함수는 엔진이 아니라 UI 계층에 둔다
- 내부 계산은 `Number`로 유지하되, 시뮬 24h에서 `Number.MAX_SAFE_INTEGER` 근접 여부를 확인한다
  (초과 조짐이 보이면 지수 표현 도입을 P3에서 검토)

## 6. 개발 도구 — `?dev=1`

첫날부터 만든다. Stage 50을 테스트한다고 실제로 30분 기다리는 일이 생기면 안 된다.

```
+10K Gold   +1M Gold   +1B Gold
Stage +1    Stage +10   보스 즉시 진입
Offline +1h  Offline +8h
게임속도  x1  x5  x20
Save   Reset Save   Export Save   Import Save
```

`?dev=1`이 없으면 패널은 DOM에 존재하지 않는다.

## 7. 세이브

```js
{ version: 1, lastSaveAt: 0, gold: 0, stage: 1, safeStage: 0, up: { atk:1, aspd:1, gold:1 }, ... }
```

- `version` 필드와 `migrateSave(save)`를 **MVP부터** 둔다
- 필드가 매일 하나씩 늘어나면 기존 세이브가 즉시 깨진다
- 마이그레이션은 누적 적용: `v1→v2→v3` 각 단계 함수를 순서대로 통과시킨다
- 알 수 없는 상위 version을 만나면 덮어쓰지 말고 백업 후 초기화한다
