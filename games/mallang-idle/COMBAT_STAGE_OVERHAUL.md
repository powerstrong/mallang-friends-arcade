# 말랑프렌즈 키우기 — 전투 화면 대개편 기획

`mallang-idle` · 전투 연출을 **실제 릴리즈 품질**로 끌어올리기 위한 전면 재설계
· 최초 작성 2026-08-16

> 이 문서는 "조금 손보면 초기 완성"이라는 판정을 **구조적으로 금지**하기 위해 쓴다.
> 각 단계마다 "이건 아직 완성이 아니다" 체크리스트를 박아 둔다. 하나라도 켜져 있으면
> 그 단계는 끝나지 않았다. 게이트 철학은 [ROADMAP.md](ROADMAP.md)와 같다 —
> **기능 수가 아니라 보는 사람의 감각으로 판정한다.**

---

## 0. 한 문장

> 지금 전투 화면은 **제자리에서 한 모션만 반복하는 자동 전투**다.
> 목표는 **"살아 있는 무대에서 우리 팀이 전진하며 싸우는 장면"** 으로 바꾸는 것이다.
> 성장·밸런스 엔진은 **한 줄도 건드리지 않는다.** 전부 표현 계층에서 해결한다.

## 1. 정직한 진단 — 왜 매력이 없는가

사용자 관찰: *"수평에 단순히 한 대 치는 모션밖에 없고, 토끼는 걷지도 않는다."*
이건 취향 불평이 아니라 **정확한 구조 진단**이다. 코드가 그렇게 만들어져 있다.

| 증상 | 코드상 원인 | 위치 |
|---|---|---|
| **토끼가 안 걷는다** | 몹 사이 전진 시간이 **0.6초**뿐. 화면 시간의 95%는 정지 상태(FIGHT/BOSS)에서 소비된다. 걷기 애니메이션은 존재하나 눈에 보일 틈이 없다 | `balance.js: advanceSeconds: 0.6` |
| **한 대 치는 모션뿐** | 공격은 `heroStrike` 돌진 키프레임 **하나**를 영원히 반복. 캐릭터별 공격은 정적 포즈(1프레임)로 스왑될 뿐, 진짜 공격 애니메이션이 없다 | `game.js: heroStrike`, `style.css: @keyframes heroStrike` |
| **뚝뚝 끊기는 걸음** | 걷기 스프라이트가 **3프레임**(453×220 = 151px×3). 달리기·정지·피격 상태가 없다 | `characters.js: frameW`, `hero-*-walk.png` |
| **평평하다 (입체감 없음)** | 시차 레이어가 배경+전경 **2장**뿐. 하늘·원경·중경·지면·전경의 겹이 없다 | `style.css: .bg-layer / .fg-layer` |
| **카메라가 죽어 있다** | 프레임이 완전 고정. 보스 등장·막타·스테이지 돌파에 줌/팬/임팩트 프레이밍이 없다 | 없음 |
| **적이 살아 있지 않다** | 몹은 등장→아이들 밥→피격 찌부가 전부. 다가오지도, 반격하지도, 예비동작도 없다. 보스는 "크기 + 타이머 바"로만 구분된다 | `style.css: enemyIdle`, `game.js: renderArena` |
| **FX가 DOM 노드 산개식** | 이펙트를 매번 `<i>`/`<span>`을 만들어 붙인다(FX_CAP 26 상한). 파티클 다수·가산 발광·궤적·잔상 같은 "즙(juice)"의 상한이 낮다 | `game.js: spawnFx` |

**중요한 반례 하나:** 지금까지 이미 5·7차에서 "즙" 패치(걷기 밥·예비동작·먼지·넉백)를
여러 번 했는데도 사용자가 여전히 밋밋하다고 느낀다. **결론: 파라미터 튜닝으로는 안 된다.**
`heroStrike` 하나에 이징을 아무리 붙여도 "한 모션 반복"이라는 사실은 안 바뀐다.
**구조를 갈아엎어야 한다.** 이 문서가 그 범위를 정한다.

### 근본 원인 한 줄

> 전투 무대가 **"엔진의 순간 계산"을 그대로 그린다.** 엔진은 몹을 `HP/DPS`초 만에 즉사시키고
> 0.6초 만에 다음 몹으로 순간이동시킨다 — 그게 그대로 화면이 되니 "볼 만한 리듬"이 없다.
> 표현 계층에 **자기만의 시계와 연출 큐**가 없다는 게 전부의 뿌리다.

## 2. "제대로 됨"의 정의 — 릴리즈 품질 기준

아래 7개 기둥이 **전부** 서야 릴리즈 품질이다. 하나라도 비면 "초기 완성"이 아니라 "미완성"이다.

- **A. 이동감(Locomotion)** — 팀이 실제로 전진하며 세계가 흘러간다. 걷기/달리기/정지가
  구분되고, 전진 구간이 "볼 만한 길이"로 느껴진다. (엔진의 0.6초와 **분리된** 연출 시계)
- **B. 전투 안무(Choreography)** — 캐릭터마다 고유 기본공격(다중 프레임) + 주기적 스킬 연출.
  같은 공격이 매번 똑같이 보이지 않는다(교대타·간헐 강타). 적은 피격·경직·처치가 다양하다.
- **C. 카메라 & 프레이밍** — 보스 등장 컷인, 막타 줌·슬로모, 돌파 순간 화면 연출. 프레임이 산다.
- **D. FX & 파티클** — 풀링된 파티클 시스템으로 스파크·파편·궤적·골드·별을 다수 동시에.
  가산 발광 레이어. 데미지 숫자의 크기/색이 타격 크기에 반응.
- **E. 적·보스 개성** — 보스가 패턴(연출)·페이즈(제한시간 임박 시 분노 틴트)·처치 세트피스를 가진다.
- **F. 가독성 & 접근성** — HP/DPS/"왜 졌는지"가 여전히 또렷하다. `prefers-reduced-motion`
  경로가 살아 있다. 모바일 60fps·배터리 예산을 지킨다.
- **G. 오디오 싱크** — 타격·크리·스킬·보스 포효·돌파 스팅이 새 애니메이션 이벤트와 맞물린다.

### 릴리즈 품질 한 줄 판정 (사람 게이트)

> **모르는 사람에게 20초 보여줬을 때 "오 이거 뭐야, 귀엽고 시원하다"가 나오는가.**
> "음... 방치형이네"가 나오면 아직 아니다.

## 3. 갈아엎을 것 / 지킬 것 / 새로 만들 것

### 3.1 절대 안 건드린다 (엔진 불변 — [AGENT_PROTOCOL.md](AGENT_PROTOCOL.md) 2절)

전투/성장/밸런스는 시뮬레이터와 **한 파일을 공유**한다. 여기 손대면 지표가 거짓말을 한다.

- `engine/combat.js` `balance.js` `save.js` `dungeon.js` `rng.js` — **한 줄도**
- `data/chapters.js` `characters.js`(스킬 수치) `quests.js` `story.js`(서사)
- 메타 UI 전부: HUD·탭·강화/편성/유물/도전/도감 패널·모달·인트로·컷신 시스템
- 오디오 엔진 코어(`audio.js`) — 후크만 추가, 절차 생성 트랙 구조는 유지
- 기존 테스트(`balance.test.js` 등) — 삭제·완화 금지

> **연출은 언제나 표현 계층에서만.** `combat.step()`이 뱉는 `state.events`를 **읽기만** 한다.
> 화면을 위해 데미지·타이밍·처치 판정을 다시 계산하지 않는다.

### 3.2 갈아엎는다 (현재 전투 화면의 내부)

- `game.js`의 아레나 렌더 뭉치: `renderArena` `renderHero` `applySprite`
  `heroStrikeFx` `followerShot` `updateCombatFx` `spawnFx`(DOM 노드식 FX) `syncLunge`
  `swapToAttackPose` — **전부 새 씬 렌더러로 이관**
- `style.css`의 아레나 구획(약 88~340행): `.field .hero .follower .enemy` +
  `heroWalk heroStrike enemySquash spawnIn bossIn` 등 CSS 키프레임 안무 — **폐기/대체**
- 캐릭터 스프라이트 모델: "3프레임 걷기 + 정적 공격 포즈 1장" → **상태별 다중 프레임 시트**
- FX 상한 26의 DOM 노드 방식 → **캔버스 파티클 풀**

### 3.3 새로 만든다

- **씬 렌더러 모듈**(`render/stage.js` 신설) — 액터·카메라·파티클·시차를 소유. 매 프레임
  엔진 상태를 읽어 그린다. UMD 패턴(무빌드), 브라우저/Node 공용은 불필요(표현 전용).
- **연출 이벤트 버퍼**(4절) — 엔진의 순간 계산과 "볼 만한 페이스"를 분리하는 핵심 부품
- **캔버스 FX/파티클 레이어** — 아레나 위 `<canvas>` 한 장. 스파크·파편·궤적·발광
- **카메라 래퍼** — 필드 전체를 감싸는 transform 대상(줌·셰이크·팬)
- **다층 시차 스택** — 하늘/원경/중경/지면/전경 (챕터별 에셋 슬롯)
- **에셋 스펙**(7절) — 상태별 프레임 수 정의. *"이미지는 나중에"* 이므로 시스템 먼저,
  플레이스홀더(단색 실루엣/도형)로 돌리고 실제 시트를 나중에 끼운다

## 4. 아키텍처 결정 — DOM 액터 + 캔버스 FX 하이브리드 (권장)

이 개편의 **가장 큰 갈림길**이다. 두 길을 저울질했다.

| | (택함) **하이브리드** | (버림) **풀 캔버스/WebGL** |
|---|---|---|
| 액터(캐릭터·적) | DOM 스프라이트, 상태 기반 다중 프레임 애니메이션 | 캔버스 스프라이트배치 |
| FX·파티클 | 아레나 위 `<canvas>` 파티클 풀 | 동일 캔버스 |
| 카메라 | 래퍼 `transform`(줌·셰이크·팬) | 캔버스 뷰 매트릭스 |
| 접근성 | `prefers-reduced-motion` **무료로 유지**(CSS 경로) | 직접 재구현해야 |
| 기존 실브라우저 테스트 | `.hero/.enemy` computed style 검증 **상당수 생존** | 전부 재작성 |
| 무빌드 정적 사이트 정합 | ✅ 그대로 | ✅(캔버스도 무빌드 가능) 하지만 코드량 급증 |
| 연출 상한(ceiling) | 귀여운 2D 아이들 게임엔 **충분히 높다** | 더 높지만 이 게임엔 과잉 |
| 리스크 | 낮음(증분 대체 가능) | 높음(작동하는 인프라·접근성·테스트 폐기) |

**결정: 하이브리드.** 근거:

1. 이 게임의 목표 톤은 "귀엽고 시원한 2D"다. 파티클·카메라·다중 프레임만 제대로 서면
   DOM 액터로도 릴리즈 품질에 도달한다. 실제 상용 아이들 게임 다수가 이 구성이다.
2. `reduced-motion`·실브라우저 회귀·모바일 검증은 이미 쌓인 자산이다. 풀 캔버스는 이걸
   전부 버린다 — [AGENT_PROTOCOL.md]가 경계하는 "작동하는 것을 이유 없이 엎기".
3. 하이브리드는 **증분 전환**이 된다. 아레나만 새 렌더러로 갈고 HUD/패널은 그대로.

> 단, "액터는 DOM"이 상한이 되면 안 된다. 액터도 **상태 머신 + 다중 프레임 시트**로
> 완전히 새로 만든다(3프레임 단일 공격 폐기). DOM은 그 스프라이트를 담는 그릇일 뿐이다.

**만약** B단계에서 DOM 액터가 프레임 드랍/합성 한계에 부딪히면, 그때 **액터 레이어만**
캔버스로 승격한다(FX 레이어가 이미 캔버스라 이관 경로가 짧다). 지금 미리 엎지 않는다.

## 5. 연출 이벤트 버퍼 — 페이싱을 엔진에서 분리 (개편의 심장)

문제: 엔진은 `advanceSeconds 0.6`초, `HP/DPS`초 만에 사건을 즉시 확정한다. 배속·복귀 시엔
한 틱에 수십 사건이 몰린다. 화면이 이걸 그대로 그리면 리듬이 없다.

해법: 표현 계층에 **자기 시계**와 **사건 큐 재생기**를 둔다.

```
combat.step(state, simDt)  →  state.events[]   (엔진: 순간 확정)
                                    │  (읽기만)
                                    ▼
        [연출 큐]  ── 재생기가 "볼 만한 페이스"로 소비 ──►  씬 렌더러
        · mob_spawn → 적 등장 연출을 T초에 걸쳐 재생
        · mob_kill  → 막타 → 처치 세트피스 → 다음 전진
        · boss_start→ 컷인 시퀀스(카메라·이름표)
```

규칙:
- **버퍼는 밸런스에 영향 없음.** 골드·스테이지·저장은 엔진이 즉시 확정한 값이 진실이다.
  버퍼는 오직 "그 사건을 언제 어떻게 보여줄지"만 늦춘다.
- **한계 지연(catch-up)**: 큐가 임계(예: 사건 1.5초분 이상)를 넘으면 재생 속도를 높여
  따라잡는다. 배속·오프라인 복귀에서 화면이 밀리지 않게. (지금 `dmgSince` 누적·타격 틱
  상한 4/s가 하던 일을 일반화한 것.)
- **전진 구간 시각 확장(A기둥 핵심)**: 엔진 전진이 0.6초라도, 큐 재생기는 몹 사이를
  **볼 만한 이동**으로 연출한다. 세계 스크롤·발걸음이 실제로 흐르도록. 단, 이건 순수 시각이며
  엔진 진행과 독립적으로 굴러가고, 밀리면 catch-up으로 흡수한다.

> 이 버퍼가 없으면 아무리 예쁜 애니메이션도 "0.6초마다 순간이동"에 잘려 안 보인다.
> **A~E 기둥 전부가 이 부품 위에 선다.** 그래서 이게 심장이다.

## 6. 단계별 개발 계획 — 각 단계에 "완성 아님" 게이트

순서는 뒤집지 않는다. 인프라(0·1) → 이동감(2) → 안무(3) → 카메라·적(4) → 마감(5).

**체크리스트 읽는 법** — 각 항목은 "이러면 아직 미완성"이라는 **실패 조건**이다.
해소되면 `[x]`로 바꾸고 **근거(테스트 이름)**를 함께 적는다. 근거 없는 `[x]`는 무효다.
그 단계의 항목이 전부 `[x]`가 되어야 다음 단계로 간다.

### 단계 0 — 씬 렌더러 골격 + 연출 버퍼 (인프라) ✅ 완료 (2026-08-16)

새 `render/stage.js`가 아레나를 소유하도록 이관. 액터·카메라·파티클·시차 레이어의
**빈 골격**과 5절의 연출 이벤트 버퍼를 세운다. 시각은 아직 플레이스홀더(도형)여도 된다.

- [x] ~~엔진 `state.events`를 큐가 소비하지 않고 game.js가 직접 그린다~~ —

## 8. 성능 · 접근성 · 검증 예산 (양보 불가)

- **성능**: 모바일 중급기 **60fps**. 파티클 풀 상한·오프스크린 컬링·`will-change` 절제.

- **접근성**: `prefers-reduced-motion`에서 **정보는 유지하고 움직임만 줄인다**(화면 끄기 아님).
  HP·보스 타이머·"필요 DPS vs 내 DPS"·데미지 숫자는 감속 모드에서도 읽혀야 한다.
- **검증**:
  - 기존 정적/실브라우저 회귀 **전부 초록 유지**(엔진 불변의 증거)
  - 신규: 씬 렌더러 시각 스냅샷(챕터별 전투/보스 — 8차 visual_smoke 방식 계승)
  - 신규: 연출 버퍼 catch-up 테스트(배속·오프라인 복귀에서 사건 유실 0)
  - 신규: 성능 예산 스모크(파티클 최대 부하 프레임타임)
  - **시각적 "재미" 최종 판정은 사람이 한다** — 스크린샷으로 재미를 판정하지 않는다

## 9. 리스크와 비-목표
